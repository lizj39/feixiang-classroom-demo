# 飞象老师 · 一句话生成课堂互动课件

> **v0.1.0** · 不配 API Key 也能完整运行

老师输入一句话，系统选出合适的教学 Skill（单个或组合），生成**可操作的课件**，
并对「为什么这么选」和「生成得对不对」给出**可核对的证据**。

```
一句话 → 理解 → 打分 → 裁决 → 编排(IR) → 渲染 → 四层验证 → 证据面板
```

## 三个硬要求怎么落地

| 要求 | 实现 |
|---|---|
| 选择可解释 | 每个候选 Skill 都有一条分数与逐条证据（命中词 / 模型能力，各自标来源）；拒绝生成时也写清原因 |
| 结果可验证 | L1 路由 → L2 IR → L3 DOM → L4 行为，四层断言；「没跑」与「通过」分开记录 |
| 故障可定位 | 分层 trace 由服务端写入；三种故障各自停在不同层，看报告停在哪层即可定位 |

## 快速开始

```bash
npm ci
npm run dev        # http://localhost:5173 —— 页面与 API 同源同端口
```

| 命令 | 作用 |
|---|---|
| `npm run verify` | `tsc --noEmit && vitest run`，当前 **275 个测试** |
| `npm run build` | 构建前端到 `dist/web` |
| `npm start` | 生产模式托管 `dist/web`（需先 build） |
| `npm run check:clean` | 交付前静态检查：真实密钥 / 本机绝对路径 / gitignore 遗漏 |
| `npm run demo:llm` | 真实调用 LLM 验证理解层（需 `.env`，不进测试） |

不需要 `npm run build` 也能开发；`dist/web` 只用于生产模式。

## 功能走查

按顺序点一遍，可以覆盖全部关键路径。

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 点 **S1** 生成 | 单 Skill：0.90 分，证据三格 |
| 2 | 点 **S2** 生成 | 组合：两个 Skill 同时达标，滑块绑定到图像 |
| 3 | 拖动滑块 | 直线按公式重算（L4 已验过） |
| 4 | 点 **S3** 生成 | 冲突平局 → 不生成，转澄清 |
| 5 | 点 **S4** 生成 | 无匹配 → 不生成 |
| 6 | 故障演练 → **drop-node** | 报告红在 L1：决策说两个，产物只有一个 |
| 7 | **break-binding** | 报告红在 L2：节点都在，绑定断了 |
| 8 | **unregistered-renderer** | 报告红在 L3：服务端全绿，页面没有滑块 |

第 8 步说明一件事：**服务端验证通过，不等于用户能看到。**

## 架构

```
                    ┌──────────────── 服务端（单进程 Express）────────────────┐
一句话 ──POST──▶    │ 理解层 IntentParser ──▶ Router ──▶ Composer ──▶ IR 校验   │
                    │   ├ 规则版（词表+正则）      │ 打分/阈值/冲突    │ 编排      │
                    │   └ LLM 版（可选）           │                  │           │
                    │                          Trace：router/composer/validator │
                    │ 验证 L1 路由 · L2 IR  ──▶ 返回 { intent, plan, IR, trace,   │
                    └──────────────────────────────── 验证报告 } ────────────────┘
                                                     │
                    ┌──────────────── 浏览器 ─────────▼──────────────┐
                    │ 渲染注册表（IR 节点 → React 组件）              │
                    │ 验证 L3 DOM · L4 行为（真的派发事件拖一次）     │
                    │ 合并成四层报告 → 证据面板                        │
                    └─────────────────────────────────────────────────┘
```

为什么 L3/L4 一定要在浏览器：它们的输入（DOM 与拖动行为）只在那里。
让服务端「验证 DOM」只能靠猜 —— 那样的验证不成立。

## 目录

```
src/contracts/   契约：skill / ir / plan / trace / verification / api / intent / scenarios
src/server/
  intent/        理解层：归一化、规则解析、参数抽取、LLM 客户端与解析器
  router/        打分、阈值、冲突检测与裁决
  composer/      把决策编排成一棵 IR
  ir/            IR 出站校验（L2 的规则）
  verify/        L1/L2 校验
  skills/        Skill 声明、校验、注册表
  trace/         分层 trace 记录器
src/web/
  render/        渲染注册表、plot 几何、滑块状态
  verify/        L3 DOM、L4 行为、报告合并
tests/           契约、编排、路由、验证、组件测试（275 个）
docs/            SPEC / CONTRACTS / 开发计划 / 故障排查指南
```

依赖方向单向：`web / server → contracts`；`contracts` 不依赖任何实现。

## 几个关键设计

**契约先行**：`tests/fixtures/*` 里的期望值写在实现之前，Router 的验收标准是「跑出来等于这里」。
否则就是「代码怎么写、测试就怎么断言」。

**整数百分制**：primary 50 / synonym 20 / intent 10 / capability 60，封顶 100。
用整数而不是 0.5+0.2 累加，是因为 `0.5 + 0.1 === 0.6000000000000001`，
会把「刚好达标」判成不达标 —— S2 的 function-plot 正好压在 0.60 上。

**遮蔽规则**：`选` ⊂ `选答案`，同一 Skill 内短词被长词遮挡，不重复计分。
被遮挡的词进 `shadowed`，界面上显示为「灰色删除线 + 0」，回答「为什么没加分」。

**依赖闭包在冲突检测之前**：补入依赖会改变参与冲突判定的集合，
顺序反了可能产出「已判无冲突、又补进一个冲突方」的坏 Plan。

**LLM 只做理解**：不产分数、不决定是否生成；失败一律降级到规则版并留痕。
prompt 里**不给词表、不给分值、不给阈值** —— 给了模型就会退化成词表复述器，
`by: 'llm'` 的证据也就不再独立。

## 故障演练与排查

左栏「故障演练」里点一下即可切换（也可用 URL：`?bug=...`）：

| 参数 | 现象 | 停在哪层 |
|---|---|---|
| `drop-node` | 课件里没有滑块，日志却说用了两个 Skill | **L1** 决策与产物不一致 |
| `break-binding` | 滑块和图像都在，绑定悬空 | **L2** 结构合法、引用断了 |
| `unregistered-renderer` | 服务端全绿，页面没有滑块 | **L3** IR 有、DOM 没有 |

定位路径与真实出错位置见 [docs/故障排查指南.md](docs/故障排查指南.md)。

## 接 LLM（可选，不配也能跑）

| 模式 | 怎么工作 | 需要 key |
|---|---|---|
| 规则版 | 词表匹配 + 正则抽参数 | 否 |
| LLM 版 | 模型读懂能力与参数，输出仍走同一套打分 | 是 |

左栏「理解方式」可切换：自动 / 规则版 / LLM 版。没配 key 时 LLM 不可点，选了也会降级并写明原因。

```bash
cp .env.example .env     # 填入 LLM_API_KEY
npm run dev
```

```
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-flash        # V4.1 Flash 在 API 里的模型名
LLM_API_KEY=sk-...
```

```bash
npm run demo:llm        # 真实调用三句话，打印意图与决策
```

三条不可动摇的约束：

1. LLM 只产出 `capabilities` / `params` / `normalized`，不产分数、不决定是否生成
2. 超时 / 401 / 非 JSON / 字段类型错 → 降级到规则版，`degraded.reason` 进 trace
3. `npm test` 全程离线（fake client），真实调用只在上面的手动脚本里

## Non-goals（有意不做）

- **不做账号、数据库、LMS 对接**：Demo 的核心是「选择可解释 + 结果可验证 + 故障可定位」
- **不做真实 LLM 决策**：模型只进理解层，裁决必须确定性
- **练习题内容是模板**：题干与选项写死在 Composer 里，不接题库；作答方式、选项数、答案校验是结构化的
- **不做移动端适配与视觉打磨**：布局只保证三栏在大屏可用、窄屏可读
- **不做跨浏览器兼容测试**：只在 Chromium 验证
- **不做性能与并发优化**：单进程、单用户场景
- **滑块固定绑定斜率 k**：没有做成 manifest 参数——产品上暂时没有「绑定到 b」的需求，
  加一个没人验证的配置项只会增加维护面
