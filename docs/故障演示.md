# 故障演示脚本（90 秒）

> 对应题面第 2 问：「日志显示互动 Skill 已调用，但课件里没有滑块 —— 怎么发现、定位、修复？」
> 结论先说：**这不是一种故障，而是三种**，各自停在不同层。

## 0. 准备

```bash
npm run dev        # http://localhost:5173
```

四个场景按钮在左侧，验证报告在右侧最下面。

---

## 1. 基线：先证明正常时是绿的（15 秒）

点 **S2 组合 Skill** → 生成。

- 中间：`y = 2x + 1` 的直线 + 一个能拖的滑块
- 右侧：**✓ 四层验证全部通过**，10 条检查全绿

**记住这个绿的样子** —— 后面每一步都要和它对比。

---

## 2. 故障一：编排丢了节点（30 秒）

地址栏末尾加 `?bug=drop-node`，回车，然后再点 S2 生成。

**你看到的**：课件里只有图像，**没有滑块**。日志（trace）里 router 明明写着
`selected: [function-plot, interactive-slider]`。

**报告在哪一层红**：`L1` —— `L1.route.selected-match` 失败，
期望 `{function-plot, interactive-slider}`、实际 `{function-plot}`。
下面 L2 四条全是 `skipped`。

**一句话定位**：决策说用了两个 Skill，产物里只有一个 → 问题在**编排**，不在渲染。

**怎么发现的**：不是靠肉眼，是 L1 这条断言本身就在比对「决策」与「产物」，
所以它必然先红。

---

## 3. 故障二：节点都在，绑定断了（20 秒）

改成 `?bug=break-binding`，再生成。

**你看到的**：图像和滑块都在，拖着好像也有数字变化。

**报告在哪一层红**：`L2` —— `L2.ir.slider-bound` 失败，证据指向
`page.children[2].bindTo.nodeId`，实际值是 `function-plot:plot-1#bug`。
注意 **L1 是绿的**：两个来源都在，决策与产物一致。

**一句话定位**：结构合法但引用断了 → 问题在**编排的绑定**，不在节点有无。
这种故障肉眼极难发现，只有校验能抓。

---

## 4. 故障三：服务端全对，页面却没有（20 秒）

改成 `?bug=unregistered-renderer`，再生成。

**你看到的**：滑块位置上是一个红框占位符：`⚠ 未注册的节点类型：slider`。

**报告在哪一层红**：`L3` —— `L3.dom.range-present` 失败，期望 1、实际 0。
而服务端返回的报告里 L1/L2 **全是绿的**。

**一句话定位**：IR 有滑块、DOM 没有 → 问题在**渲染注册表**。
这也是三条里最接近题面描述的那一条：日志（服务端）说调用了，用户看不到。

**关键点**：如果只在服务端做验证，这条故障永远发现不了。L3/L4 必须在浏览器跑，
这不是设计偷懒，而是分工的必然。

---

## 5. 修复与回归（5 秒）

去掉 `?bug=` 参数，重新生成 → 四层全绿。

三个开关都是**演示用的故障注入**，真实修复对应三处代码：

| 故障 | 真实修复位置 | 拦它的回归测试 |
|---|---|---|
| drop-node | `composer/compose.ts` 不能丢节点 | `tests/verify/fault-demo.test.ts`「没有故障时全绿」 |
| break-binding | 绑定必须在本次合并结果里可解析 | 同上 + `tests/ir/validate.test.ts` 的 `binding-resolves` |
| unregistered-renderer | `render/registry.tsx` 必须覆盖全部节点类型 | `tests/web/courseware.test.tsx`「注册表覆盖 IR 全类型」 |

最后那条覆盖率断言是真正的守门员：**新增节点类型忘了注册渲染器，测试立刻红**。

---

## 面试时可以补的一句

> 这套验证的价值不在于「发现了 bug」，而在于**把故障定位变成一次查表**：
> 先看报告红在哪一层，再看 trace 里那一层的输入输出，就知道是哪段代码的问题。
> 三层故障对应三个不同的停点，不需要靠猜。
