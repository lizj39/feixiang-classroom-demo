# 开发计划

> 里程碑、验收判据与已知边界。
> 原则：每个里程碑都要能独立验收 —— 先写下「什么现象算通过」，再写实现。

## 1. 背景与目标

教师用一句话描述想要的教学素材，系统需要自己判断该用哪些教学能力（画图、滑块互动、随堂练习），
生成一个可操作的课件，并且对「为什么这么选」和「生成得对不对」给出可核对的证据。

三条产品要求决定了整个架构：

| 要求 | 架构上的对应 |
|---|---|
| 选择可解释 | 声明式 Skill manifest + 可打分的证据链 + 分层 trace |
| 结果可验证 | 四层断言：路由 → IR → DOM → 行为 |
| 故障可定位 | 每层留下输入输出快照，故障停在哪层一目了然 |

## 3. 验收判据怎么定

四条规则，缺一条判据就不可信：

1. **可证伪**：必须能说出「出现什么现象算失败」。说不出就不是判据，是感想。
2. **产物级优于调用级**：断言 DOM / 节点 / 像素 / state，而不是「mock 被调用了几次」。
   日志说调用了不算数 —— 这是整个验证体系的出发点。
3. **契约先行**：判据从规格反推、先于实现写下。先写 fixtures 再写路由，先生成注册表覆盖率断言再写渲染器。
4. **双向可追溯**：需求每句话 → 至少一条判据；每条判据 → 能说回哪条需求。任一方向断路就是漏项。

判据的客观性分三档，交付时要能说出哪些是自动的、哪些靠人：

| 档 | 含义 | 本项目的例子 |
|---|---|---|
| A | 可全自动断言 | 契约、路由、编排、IR 校验、L1–L4 验证（共 27 类） |
| B | 半客观，需人按步骤判定 | 新同事照 README 能否跑通 |
| C | 主观 | 5 分钟能否讲清取舍 |

## 4. 覆盖矩阵

| 产品要求 | 对应实现与测试 |
|---|---|
| 选择可解释 | 得分表（每条证据带来源与分值）、冲突裁决理由、澄清问题 |
| 结果可验证 | L1–L4 四层断言 + 前后端合并报告 |
| 故障可定位 | 三种注入模式 + 分层 trace + 定位路径文档 |
| 离线可用 | 默认规则版；LLM 可选且失败降级 |

**明确不覆盖**（写进 README 的 Non-goals，避免误解）：

真实 LLM 决策路径、跨浏览器兼容、性能与并发、视觉回归、题库内容、更多故障模式的归纳。

## 5. 风险与取舍

| 风险 | 处置 |
|---|---|
| 范围膨胀 | 固定 4 个 Skill、5 种 IR 节点；不做账号 / 数据库 / LMS |
| 前端耗时过多 | 不装 UI 库，布局用 Grid，把力气放在证据面板 |
| 判据全绿却讲不清 | 判据只保证不塌；表达靠演练（见下） |
| 被问「怎么知道覆盖全了」 | 用第 4 节矩阵回答，并主动说出不覆盖项 |

## 6. 后续可做

- 题库接入：`exercise` 节点的题干与选项改为由 Skill 参数驱动
- 滑块支持绑定任意可调参数（现在固定绑定斜率 k）
- 更多 Skill 类型（几何作图、分步讲解）
- LLM 少样本示例优化：用真实 badcase 当示例，而不是凭空编写案例
