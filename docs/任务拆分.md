# 任务拆分 V1（决策已锁定，未开始实现）

## 0. 已锁定的三个决策

| 决策 | 选择 | 产生的后果 |
|---|---|---|
| 后端 | **Node API**（薄后端） | 决策链与 trace 在服务端生成；`POST /api/generate` 返回 `plan/ir/trace/verification`；`npm run dev` 仍是单命令 |
| 技术栈 | **Vite + React + TypeScript** | 契约 = 类型；渲染注册表 = `Record<NodeType, Component>`；不装 UI 库/路由/状态库，图用原生 SVG 画 |
| Skill 集合 | **4 个**：`function-plot`、`interactive-slider`、`exercise-choice`、`exercise-input` | 冲突对 = choice × input（同题位互斥）；候选池 4 个，使「都不合适」可信 |

**系统形态**：单 Node 进程（Express/Fastify 提供 `/api/generate`，生产模式顺带托管静态产物），前端 Vite dev 时经 proxy 访问。无数据库、无鉴权、无持久化。

**链路**：`一句话 → Router(选谁) → Composer(怎么拼) → IR(中间产物) → Renderer(怎么画) → Validator(对不对) → 证据面板`
每一层产出可序列化快照，trace 由服务端逐层写入。

## 1. 五个契约（实现前手写定稿）

1. **Skill Manifest**：`id / capabilities(关键词+同义词) / produces(IR 节点类型) / requires / conflictsWith / priority / 题位槽位 / paramSchema / namespace`
2. **课件 IR**：节点类型封顶 5 种 —— `page / plot / slider / text / exercise`
3. **Trace 事件**：`{ layer, seq, at, input, output, decision, reason }`，layer ∈ `router / composer / renderer / validator`
4. **验证结果**：`{ ruleId, layer(L1-L4), status, evidence(节点路径/DOM 选择器/实际值), message }`
5. **冲突策略**（必须定死，否则测试写不出来）：`conflictsWith` 对称校验 → 按 `priority` 高者胜 → **同优先级平局 = 全部不选，降级为澄清**

**决策参数**（V1.1 已修订，详见文末修订记录）：整数百分制计分，展示值 = `points / 100`；**单阈值 `0.60`**，达到即入选，低于即不选；入选集为空 → `no_match`。

## 4. 判据是怎么定出来的

四条规则，缺一条判据就不可信：

1. **可证伪**：必须能说出「出现什么现象算失败」，否则不是判据，是感想。
2. **产物级优于调用级**：断言 DOM / 节点 / 像素 / state，而不是「mock 被调用了几次」。日志说调用了不算数——这正好是题面第 2 问的靶心。
3. **契约先行**：判据从 SPEC 反推、先于实现写下；先写 fixtures 再写 router，先写 registry 覆盖率断言再写渲染器。
4. **双向可追溯**：题面每句话 → 至少一条判据；每条判据 → 能说回题面哪句话。任一方向断路就是漏项。

**为什么不满足于「path 属性变了」**：变化 ≠ 正确。所以 P4-3 改成数值断言（x=0 时曲线在 y=1 处），P4-4 要求两种参数下都按公式对。这是把「假互动」与「真联动」区分开的关键。

## 5. 覆盖矩阵与明确不覆盖项

| 题面要求 | 对应任务 |
|---|---|
| 怎么选（单用/搭配/冲突/都不合适） | P2-2、P3-1~P3-4、P5-1~P5-3 |
| 怎么确认用对了（发现/定位/修复） | P6-1~P6-4、P7-1~P7-3 |
| 可本地运行 | P1-1、P8-1、P8-2 |
| 独立选择理由可解释 | P3-1（打分明细）、P6-1（trace） |

**不覆盖（主动写进 README 的 Non-goals）**
- 真实 LLM 决策路径（只有 adapter 接口，无 E2E）
- 跨浏览器兼容（只验证 Chromium）
- 性能、并发、多用户
- 视觉/交互美观度（无视觉回归）
- 教学内容的数学正确性全量校验（只验证 2 个采样点）
- 未知故障模式的定位能力（只归纳验证了 2 类已知故障）
- 用户输入注入的 XSS 防护（若时间允许，补一条「输入 `<img onerror>` 后不执行」的断言）

## 7. 修订记录

### V1.1（阶段 0 落定，2026-11-16）

实现契约时发现四处规格漏洞，回头改了任务拆分本身：

| 原方案 | 改为 | 为什么 |
|---|---|---|
| 拒绝场景统一叫 `clarify` | 拆成 `conflict`（带 `resolution`）与 `no_match` | 合成一个类型就丢掉了「多个都想要但打架」和「一个都不合适」的区别，而这正是题面第 1 问要问的两种情况 |
| 双阈值 0.6 / 0.3（有「候选」档） | **单阈值 0.60** | 双阈值会把弱匹配悄悄变成「将就用」，与「敢说不生成」直接矛盾 |
| 浮点加分（0.5 + 0.1） | **整数百分制**（50/20/10，上限 100） | `0.5 + 0.1 === 0.6000000000000001`，会把「刚好达标」判成不达标；S2 的 0.60 正好压在阈值上，必须精确 |
| 同义词重复计分 | 加**遮蔽规则**（token 是另一命中 token 的子串时忽略） | 「选答案」和「选」不能各加一次分，否则分数失去意义 |
| 冲突只查显式声明 | 显式 `conflictsWith` **+ 同 `slot` 抢占** | 前者是约定，后者是结构事实；只靠前者，漏声明就会静默拼出两个抢同一题位的节点 |
